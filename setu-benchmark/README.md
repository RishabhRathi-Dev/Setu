# Setu benchmarks and chaos tests

All load and failure testing lives under `src/test/java/io/setu/benchmark/chaos`. CI runs every chaos test against the actual TCP server, synchronous client, and broker in both storage modes. `QuickBrokerChaosBenchmarkTests` drives sixteen producers and sixteen independent consumer members through 20,000 256-byte records in 256-record produce batches, exercises fetch paging and file-segment rotation, abandons one consumer with an outstanding acknowledgement, verifies expiry and continued progress, and restarts the broker. `BrokerLimitsChaosTests` drives sixteen producers and sixteen consumers through 16,000 records while exercising size boundaries and segment rotation. Both bounded workloads have five-minute deadlines; the acknowledgement expiry remains 250 ms.

`ProgressiveCapacityChaosTests` launches a separate JVM with a 768 MiB maximum heap for each storage mode. Each run doubles producer and consumer connections at every stage, continuously produces 256-record batches and fetches/acknowledges records over TCP, and reports per-stage throughput, approximate p99 request latency, process CPU, heap use, and the capacity stop reason. It continues until sustained process CPU saturation, JVM heap exhaustion, or an operating-system resource limit ends the ramp. The child process contains heap OOM so it can be reported without taking down Maven or the host. The README badges show each mode's terminal stage, stop reason, peak observed producer/consumer rates, CPU, heap, and p99 latency. These measurements vary by machine and are not pass/fail throughput thresholds.

For controlled experiments, set `setu.benchmark.batch.records` (1–10,000, default 256), `setu.benchmark.stage.millis` (250–60,000, default 2,000), and `setu.benchmark.max.concurrency` (zero for the unbounded ramp, or a power of two up to 32,768). The test forwards these properties into its isolated worker JVM. Each worker reports `CAPACITY_CONFIG` so its workload is explicit. A bounded ramp ends with `CONFIGURED_LIMIT`; it does not establish the host's terminal capacity. This plaintext workload bypasses security quotas.

The measured workload still uses the same payload, batching, and stage-duration defaults. It now runs a separate two-second warmup before stage 1 (`setu.benchmark.warmup.millis`, 0–60,000; zero restores a cold start). Warmup counters are reported as `CAPACITY_WARMUP` and excluded from rates and badges. Its consumer leaves the warmup group before measurement, releasing retained memory records. CPU utilization is calculated from process CPU-time deltas divided by elapsed time and the CPUs available to the JVM; this avoids the OS load accessor's host-wide denominator under affinity restrictions. Four consecutive 250 ms samples at or above 92% trigger the CPU hold described below before the unbounded ramp stops. Bounded experiments report CPU utilization but run the full requested measurement window instead of exiting early on CPU saturation; OOM, resource limits, and request failures still terminate them. CPU figures include both the broker and load clients in the same JVM. Historical cold-start runs and results from hosts with different CPU/disk allocations are not directly comparable.

The isolated progressive worker explicitly disables the broker's retained-memory log budget to preserve its intentional exhaustion workload and historical profile. `CAPACITY_CONFIG` reports `memory_log_budget=unlimited`. Normal memory brokers use the shared 256 MiB budget; the separate backpressure tests exercise quota rejection and recovery instead of exhausting the heap.

Benchmark logging defaults to INFO so request traces do not dominate throughput. Add `-Dsetu.log.level=DEBUG` for a diagnostic run; this is forwarded into the worker and changes the measurement overhead. `CAPACITY_RUNTIME` records the Java/OS versions, CPU count, heap limit, logging profile, and TCP_NODELAY setting. `CAPACITY_PREPARE` identifies a stage even if its setup fails, and `CAPACITY_DIAGNOSTICS` adds live platform-thread count and cumulative GC time after each completed stage. The first load failure prints a complete exception chain with operation context. Heap exhaustion uses a preallocated marker and emergency reserve before halting with exit 42; unknown crashes still fail the test.

`CAPACITY_CAPTURE` prints the retained directory under root `logs/benchmarks/capacity/`, containing worker stdout/stderr (`capacity.log`) and rolling operational logs (`setu.log`). These captures survive temporary broker-data cleanup. CI uploads the `benchmark-diagnostics` artifact even when a benchmark fails, including captures and Surefire reports. Other Java test modules keep their existing quiet test logging configuration.

The 11 October storage/batching experiment exceeded 1M produced 512-byte records/s with larger batches while consumers accumulated backlog; those results use a different profile from the published default benchmark badges. Local working notes stay in the ignored `docs/` directory, and diagnostic captures belong under the ignored `logs/` directory.

CI runs the 4,096-record, 12-second file experiment with up to two producers/consumers as a separate step before capacity exhaustion. Its results appear in the workflow log and the large-batch capture. The badge input contains only the default progressive capacity capture, keeping the batching profiles separate.

CI pins INFO logging and all capacity profile parameters explicitly. Each benchmark step retains its own capture: `bounded-chaos.log`, `capacity-large-batch.log`, or `capacity-default.log`. Badge generation reads only the explicit default capture and cannot fill gaps from stale Surefire XML belonging to another profile. Both modes must still complete their first measured stage and report a recognized stop reason; raising throughput by skipping load checks or hiding CPU exhaustion is not part of this profile.

`CAPACITY_STORAGE` identifies the data filesystem and available space. A file run on tmpfs measures the file-code path on RAM storage, not durable-disk throughput; compare disk results using the same filesystem and host allocation. Temporary filesystem capacity can terminate a file ramp before JVM memory is exhausted, and the operational log preserves the underlying storage exception.

After four consecutive high-CPU samples, the unbounded ramp now holds the same producer/consumer concurrency for ten seconds before reporting CPU saturation. Set `setu.benchmark.cpu.hold.millis` (0–60,000; default 10,000) to change this window; zero restores the immediate stop. The current stage extends as needed, so a two-second ramp stage can include a ten-second hold. `CAPACITY_CPU_HOLD_BEGIN` identifies the trigger and `CAPACITY_CPU_HOLD_END` reports the hold's own production/delivery rates and average CPU, separately from the full-stage totals. CPU may dip during this observation window; the load remains fixed and the observed CPU is reported. Errors, stalls, storage exhaustion, and OOM can end the hold early. Bounded and warmup runs retain their configured duration and do not trigger a CPU hold. CI explicitly selects the ten-second hold.

The completed ramp prefix is emitted as `CAPACITY_STAGE` when the hold begins, preserving a measurement if OOM interrupts the hold. `CAPACITY_STAGE_TOTAL` reports the combined ramp-plus-hold window afterward. Peak-rate badges and target progress consider measured ramp stages and completed holds; partial or zero-duration holds cannot become sustained peak results. Capacity badges use the final combined-window diagnostics when available. The separate hold table reports the longer observation window and whether it completed. A missing hold-end record means the hold was interrupted; the terminal `CAPACITY_STOP` identifies the boundary instead of claiming a completed sustained result.

The top-level README uses self-contained Shields badge URLs, so metrics remain visible even when the repository does not expose raw files publicly. After a successful master run, the workflow parses the progressive test output, refreshes the capacity and peak-rate JSON, updates the badge URLs in the README, and pushes the data with `[skip ci]`. Pull request and non-master runs do not update the published badges.

Functional end-to-end requirements belong to `setu-integration-tests`; crash, expiry, malformed traffic, concurrent stress, and resource exhaustion are benchmark chaos cases. CI runs unit tests, all integration tests, then every bounded chaos test. It runs progressive capacity tests last so their CPU and memory exhaustion cannot interfere with bounded test deadlines. Maven builds upstream modules to resolve reactor dependencies, while Surefire filters execution to the integration or chaos classes for each stage.

Run it from the repository root with Java 25:

```powershell
.\mvnw.cmd -pl setu-benchmark -am '-Dtest=*ChaosTests,!ProgressiveCapacityChaosTests,QuickBrokerChaosBenchmarkTests' -Dsurefire.failIfNoSpecifiedTests=false test
.\mvnw.cmd -pl setu-benchmark -am '-Dtest=ProgressiveCapacityChaosTests' -Dsurefire.failIfNoSpecifiedTests=false test
```
