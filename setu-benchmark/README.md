# Setu benchmarks and chaos tests

All benchmark JVMs use `-XX:+UseZGC -XX:+UseStringDeduplication`, including the isolated capacity, steady broker/client, crash, and OOM workers. Child workers check both options and print `BENCHMARK_RUNTIME ... string_dedup=true gc=...` before starting. Their `ProcessBuilder` commands supply the options explicitly because child JVMs do not inherit Maven's JVM flags. Capacity reports include both settings; older captures without those fields are labeled `unrecorded`. Broker AOT caches are generated from packaged JARs by the server launcher; tests use reactor class directories and measure their own JVM processes. Compare runs using their runtime and workload configuration.

## Payload comparisons and host budgets

Use Java 26 and Python 3 on Linux or WSL with systemd and cgroup v2. The benchmark launcher detects the current CPU affinity, ancestor CPU quotas, available RAM, ancestor memory limits/usage, CPU model, and free space on the data filesystem. It prints `BENCHMARK_RESOURCES` and saves `resources.json` beside every capture. The default `host` profile uses the machine's actual allocation, so the same configuration scales from a GitHub Linux runner to a larger local machine. It allocates 80% of available CPU and RAM by default, leaving 20% available to other work. Available RAM accounts for processes already running; the reservation is not calculated solely from installed RAM.

```bash
# Inspect current specifications and the planned budget without starting a benchmark.
python3 scripts/run-benchmarks.py --dry-run

# Default matched comparison: 256/512/1024/4096 bytes, three repeats, 1/2/4/8 clients.
python3 scripts/run-benchmarks.py

# Reproduce the resource ceiling of a standard private GitHub Linux runner locally.
python3 scripts/run-benchmarks.py --profile github-private

# Independent CPU/RAM shares, alternate sizes and longer measurement windows.
python3 scripts/run-benchmarks.py --cpu-fraction .85 --memory-fraction .75 \
  --payload-sizes 512,1024,4096 --stage-millis 10000 --repeats 3
```

`--fraction` sets the shared default (0.8); `--cpu-fraction`, `--memory-fraction`, and `--disk-fraction` override it separately. Fractions must be greater than zero and at most one. CPU quotas are rounded down to 1% of one core, preserving headroom on two-core runners without discarding an entire core. `github-private` caps the detected allocation at two CPUs/8 GiB; `github-public` caps it at four CPUs/16 GiB, based on the [current standard runner specifications](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). These ceilings never increase the resources available on a smaller host and do not reproduce runner CPU speed or disk performance.

The launcher uses a transient systemd service with `CPUQuota`, `MemoryMax`, `MemoryHigh`, and swap disabled. All descendants, including Maven, Surefire, the broker, and load clients, share the same enforced envelope. It runs the workload as the invoking user; non-root users need passwordless sudo for `systemd-run` (available on standard GitHub Ubuntu runners). No silent fallback to unbounded execution is permitted. In WSL, enable systemd if it is not already running. Process-tree cleanup applies on failure or interruption. Resource-limit kills fail the run and cannot become successful benchmark results.

Within the memory envelope, Maven gets a 512 MiB heap and Surefire 256 MiB. After allowing for those launchers, each worker gets a share with 60% assigned to heap and 10% to direct buffers, leaving the rest for native allocations and charged file cache. Steady broker and client JVMs split the worker allowance; they do not each receive 80% of the host. Retained message memory defaults to one quarter of each worker heap, capped below 2 GiB. `--heap-mib`, `--direct-mib`, and `--memory-log-mib` allow smaller controlled allocations; validation prevents overrides consuming native headroom. The progressive file worker checks free disk space once per second and stops at the configured reserve; this is a sampled guard rather than a filesystem quota, so writes already in flight can cross the threshold. `--data-directory` selects the temporary data filesystem (default: the system temporary directory).

Each payload uses the same host snapshot, resource budget, 256-record batches, warmup, stage duration and concurrency stages. Sizes rotate between repeats to reduce order bias; runs execute sequentially. Console output, `comparison.txt` and `comparison.json` contain per-stage medians, ranges, payload MiB/s, p99 and CPU utilization. Consumer rates include fanout and are not unique end-to-end delivery rates. Only completed stages through the configured ceiling qualify: early OOM, missing stages and mixed payload captures fail validation. These bounded comparisons do not establish terminal capacity. Raw captures and JFR remain under `logs/benchmarks/`; local comparisons never overwrite published badges.

`setu.benchmark.record.bytes` configures progressive and steady workers (1–65,536 bytes, default 1,024). The payload/batch combination must fit the 15 MiB frame limit. Direct Maven calls retain the historical 768 MiB capacity heap, 512 MiB steady heaps and 256 MiB retained-memory default; use the Python launcher for detected and enforced host budgets. `--kind steady`, `--kind large-batch`, `--kind capacity`, and `--kind chaos` run the other CI profiles inside the same policy, with one explicit `--payload-sizes` value. The unbounded capacity profile still runs last. CI publishes the payload comparison in its job summary and retains all reports in `benchmark-diagnostics`; badge generation continues to read only the default capacity capture. Workflow dispatch inputs or repository variables `SETU_BENCHMARK_FRACTION` and `SETU_BENCHMARK_PAYLOADS` configure the policy and sweep; automatic runs default to 80% and the four standard sizes.

## Historical decoder and GC review

The default payload is 1,024 bytes for progressive, steady, bounded chaos, and application AOT training; progressive batches remain 256 records. Published measurements retain the size used by their run. The master benchmark reviewed during the original decoder/AOT change used 512-byte payloads, with peak ingestion of 368.78K records/s in memory and 420.68K records/s with file storage. It showed near-saturated CPU, substantial allocation, and memory backpressure despite low recorded GC pause overlap. Samples included file append/read and group commit, request construction, payload decoding, framing, and fetch response encoding/decoding. Accordingly, AOT training exercises real concurrent clients and both storage paths, plus mTLS authentication, authorization, quotas, and retained-memory rejection/reclamation. Its bounded workload prepares these paths without running the exhaustion ramp; it does not establish a throughput improvement.

A Java 25.0.2 comparison on Windows 11 with 12 available processors used 512-byte records, 256-record batches, a two-second warmup, four three-second stages through eight producers/eight consumers, a 768 MiB maximum heap, and JFR. In the final stage, G1 versus the updated decoder with ZGC recorded file GC pause overlap of 188.658 versus 1.682 ms and memory overlap of 352.286 versus 8.888 ms. File ingestion measured 655,798 versus 727,508 records/s; memory ingestion measured 631,594 versus 530,322 records/s. Pause overlap is accumulated time inside the stage, not the longest pause. Throughput was mixed; these short runs do not establish terminal capacity or a consistent ingestion gain.

An isolated fetch decoder comparison measured median rates of 15.17 versus 18.96 million records/s across three warmed two-second rounds, approximately 25% faster. Allocation remained essentially unchanged at about 153 KiB per 256-record frame; private payload arrays dominate. These historical measurements predate the Java 26 upgrade, string deduplication, and broker AOT workflow. Raw captures are in the ignored `metrics-*.log` files and `logs/benchmarks/capacity/`. Remaining sampled costs include payload copies, file reads, and fetch encoding.

`IsolatedThroughputBenchmarkTests` measures sustainable load separately from the exhaustion ramp: broker and clients run in different JVMs, four producers target 10,000 records/s, and one consumer reads either one or four partitions without broadcast amplification. It reports independent produce/fetch/ack histograms, scheduling delay, missed offered slots, drain time, and broker-only CPU/heap metrics. CI retains `steady-throughput.log` and the captures under `logs/benchmarks/steady/`.

Server request/response admission can stop the exhaustion ramp with a clean quota rejection or connection close before JVM OOM. File producers retry the explicit partition-write-queue-full response with 1 ms backoff and a five-second recovery deadline; `CAPACITY_BACKPRESSURE` includes these waits, and successful produce latency includes retry time. Other file quota rejections remain failures. This lets the 1,024-byte profile exercise bounded writer backpressure while keeping the production 32 MiB queue limit. Stage counts are not directly comparable to earlier runs that stopped at the first write-queue rejection or lacked these controls.

All load and failure testing lives under `src/test/java/io/setu/benchmark/chaos`. CI runs every chaos test against the actual TCP server, synchronous client, and broker in both storage modes. `QuickBrokerChaosBenchmarkTests` drives sixteen producers and sixteen independent consumer members through 20,000 1,024-byte records in 256-record produce batches, exercises fetch paging and file-segment rotation, abandons one consumer with an outstanding acknowledgement, verifies expiry and continued progress, and restarts the broker. `BrokerLimitsChaosTests` drives sixteen producers and sixteen consumers through 16,000 1,024-byte records while exercising size boundaries and segment rotation; concurrent fetches use 1 MiB pages to fit the shared response budget. Both bounded workloads have five-minute deadlines. BrokerLimits uses a ten-second acknowledgement deadline and polls for eviction so file reads on busy CI hosts do not falsely expire healthy consumers; the smaller expiry scenarios retain their short deadlines.

`ProgressiveCapacityChaosTests` launches a separate JVM with a 768 MiB maximum heap for each storage mode. Each run doubles producer and consumer connections at every stage, continuously produces 256-record batches and fetches/acknowledges records over TCP, and reports per-stage throughput, approximate p99 request latency, process CPU, heap use, and the capacity stop reason. Both modes must complete at least eight stages (128 producers and 128 consumers), then continue doubling until heap exhaustion, an operating-system resource limit, or a real request failure/stall ends the ramp. CPU saturation remains observable and does not stop the ramp. A runtime failure before the required floor fails validation and prevents badge publication; it is never treated as a completed stage. The child process contains heap OOM so it can be reported without taking down Maven or the host. The generated top-level README badges and tables are the published benchmark results; local runs do not overwrite them.

For controlled experiments, set `setu.benchmark.batch.records` (1–10,000, default 256), `setu.benchmark.stage.millis` (250–60,000, default 2,000), and `setu.benchmark.max.concurrency` (zero for the unbounded ramp, or a power of two up to 32,768). The test forwards these properties into its isolated worker JVM. Each worker reports `CAPACITY_CONFIG` so its workload is explicit. A bounded ramp ends with `CONFIGURED_LIMIT`; it does not establish the host's terminal capacity. This plaintext workload bypasses security quotas.

The default capacity workload uses 1,024-byte payloads, 256-record batches, two-second stages, and a separate two-second warmup (`setu.benchmark.warmup.millis`, 0–60,000). Warmup counters are excluded from rates and badges. CPU utilization uses process CPU-time deltas divided by elapsed time and the configured fractional CPU budget (or available JVM CPUs for direct Maven runs). Four consecutive 250 ms samples at or above 92% trigger the observation hold described below from stage eight onward. Bounded experiments and warmup run their full configured windows without a CPU hold. CPU figures include both the broker and load clients in the same JVM.

The progressive worker now uses the broker's shared 256 MiB retained-memory budget. Memory producers pause when retained log ownership reaches half the budget, and retry a quota rejection while consumers acknowledge and reclaim records. Each completed stage leaves its consumer group, releasing its remaining memory backlog before the next stage; setup, cleanup, checkpoints, and draining in-flight requests are outside measured rates. `CAPACITY_BACKPRESSURE` reports pacing/retry waits, and `CAPACITY_RELEASE` reports remaining log ownership. This avoids exhausting the heap on accumulated old-stage backlog before connection scaling is measured. Transient protocol buffers and connection state can still reach real JVM OOM. Configure `setu.benchmark.memory.log.bytes` to change the budget; zero explicitly restores unlimited retention. `setu.benchmark.min.stages` controls the required floor (1–16, default 8); a bounded experiment below that floor is permitted. This profile differs from earlier unlimited-backlog/CPU-stop runs, so their terminal stages are not directly comparable.

JFR is enabled by default (`setu.benchmark.jfr=true`) with Java's `profile` configuration and a 128 MiB disk-recording bound. A custom stage event marks each measured interval. After the worker exits, the parent reads `capacity.jfr` and emits `CAPACITY_JFR`: estimated allocation bytes from allocation-sample weights, recorded GC pause overlap, CPU sample count, and the hottest sampled method. Warmup and stage cleanup are excluded. Throughput and p99 continue to use completed TCP operations and the request histogram; JFR supplies diagnostic evidence and its overhead is part of the explicit CI profile. The generated README includes per-stage JFR diagnostics and a JFR badge for each mode. Recordings are checkpointed outside measurement using a temporary file and replacement, so a failed OOM dump preserves the last valid capture; the terminal partial stage may lack JFR data. Missing JFR for any required stage blocks badge publication.

Benchmark logging defaults to INFO so request traces do not dominate throughput. Add `-Dsetu.log.level=DEBUG` for a diagnostic run; this is forwarded into the worker and changes the measurement overhead. `CAPACITY_RUNTIME` records the Java/OS versions, CPU count, heap limit, logging profile, and TCP_NODELAY setting. `CAPACITY_PREPARE` identifies a stage even if its setup fails, and `CAPACITY_DIAGNOSTICS` adds live platform-thread count and cumulative GC time after each completed stage. The first load failure prints a complete exception chain with operation context. Heap exhaustion uses a preallocated marker and emergency reserve before halting with exit 42; unknown crashes still fail the test.

`CAPACITY_CAPTURE` prints the retained directory under root `logs/benchmarks/capacity/`, containing worker stdout/stderr (`capacity.log`), JFR (`capacity.jfr`), and rolling operational logs (`setu.log`). These captures survive temporary broker-data cleanup. CI uploads the `benchmark-diagnostics` artifact even when a benchmark fails, including captures and Surefire reports. Other Java test modules keep their existing quiet test logging configuration.

The 11 October storage/batching experiment exceeded 1M produced 512-byte records/s with larger batches while consumers accumulated backlog; those results use a different profile from the published default benchmark badges. Local working notes stay in the ignored `docs/` directory, and diagnostic captures belong under the ignored `logs/` directory.

CI runs the 4,096-record, 12-second file experiment with up to two producers/consumers as a separate step before capacity exhaustion. Its results appear in the workflow log and the large-batch capture. The badge input contains only the default progressive capacity capture, keeping the batching profiles separate.

CI pins INFO logging and all capacity workload parameters explicitly. CPU, heap, direct buffers and retained memory are derived from detected resources and the configured fraction. Each benchmark step retains its own capture: `bounded-chaos.log`, `capacity-large-batch.log`, or `capacity-default.log`; payload sweeps retain separate captures for every size/repeat. Badge generation reads only the explicit default capture and cannot fill gaps from stale Surefire XML belonging to another profile. It validates both modes' stages 1–8, JFR diagnostics, and recognized stop reasons before writing any badge or README output. Target-progress tables report payload MiB/s alongside records/s so changes in record size remain visible.

`CAPACITY_STORAGE` identifies the data filesystem and available space. A file run on tmpfs measures the file-code path on RAM storage, not durable-disk throughput; compare disk results using the same filesystem and host allocation. Temporary filesystem capacity can terminate a file ramp before JVM memory is exhausted, and the operational log preserves the underlying storage exception.

From the required stage onward, four consecutive high-CPU samples hold the same concurrency for ten seconds, then the ramp continues doubling. Set `setu.benchmark.cpu.hold.millis` (0–60,000; default 10,000) to change this observation window; zero disables its extra duration. `CAPACITY_CPU_HOLD_BEGIN` identifies the trigger and `CAPACITY_CPU_HOLD_END` reports hold-specific rates and average CPU separately from full-stage totals. Errors, stalls, storage exhaustion, and OOM can interrupt the hold. CI explicitly selects the ten-second hold.

The completed ramp prefix is emitted as `CAPACITY_STAGE` when the hold begins, preserving a measurement if OOM interrupts the hold. `CAPACITY_STAGE_TOTAL` reports the combined ramp-plus-hold window afterward. Peak-rate badges and target progress consider measured ramp stages and completed holds; partial or zero-duration holds cannot become sustained peak results. Capacity badges use the final combined-window diagnostics when available. The separate hold table reports the longer observation window and whether it completed. A missing hold-end record means the hold was interrupted; the terminal `CAPACITY_STOP` identifies the boundary instead of claiming a completed sustained result.

The top-level README uses self-contained Shields badge URLs, so metrics remain visible even when the repository does not expose raw files publicly. After a successful master run, the workflow parses the progressive test output, refreshes the capacity and peak-rate JSON, updates the badge URLs in the README, and pushes the data with `[skip ci]`. Pull request and non-master runs do not update the published badges.

Functional end-to-end requirements belong to `setu-integration-tests`; crash, expiry, malformed traffic, concurrent stress, and resource exhaustion are benchmark chaos cases. CI runs unit tests, all integration tests, then every bounded chaos test. It runs progressive capacity tests last so their CPU and memory exhaustion cannot interfere with bounded test deadlines. Maven builds upstream modules to resolve reactor dependencies, while Surefire filters execution to the integration or chaos classes for each stage.

Run it from the repository root with Java 26:

```powershell
.\mvnw.cmd -pl setu-benchmark -am '-Dtest=*ChaosTests,!ProgressiveCapacityChaosTests,QuickBrokerChaosBenchmarkTests' -Dsurefire.failIfNoSpecifiedTests=false test
.\mvnw.cmd -pl setu-benchmark -am '-Dtest=ProgressiveCapacityChaosTests' -Dsurefire.failIfNoSpecifiedTests=false test
```
